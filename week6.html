Concurrency and parallelism

Concurrent work: Several activities make progress over overlapping periods. One core can interleave them.

Parallel execution: Two or more activities execute at the same instant on separate processing resources.

A race can occur with interleaving on one core.

Further reading

Threads and shared state

Shared within a process: Code, heap and other process resources can be accessible to several threads.

Private execution state: Each thread has its own execution position, register state and stack.

Sharing makes communication convenient and coordination necessary.

Further reading

The lost-update sequence

Worker A: Read 0 → add 1 locally → write 1.

Worker B: Read 0 before A writes → add 1 locally → write 1.

Two completed increments can leave the shared value at 1.

Test a remedy: Protect the entire update. Compare the trace and explain the cost of waiting.

Critical sections and mutexes

Boundary: Protect every operation needed to preserve the shared-state invariant.

Ownership: One owner enters; contenders wait. Release ownership when the critical section ends.

Correctness depends on every relevant code path following the same protocol.

Further reading

Granularity and synchronisation cost

Coarse protection: A broad lock is easier to reason about but may serialise independent work.

Fine protection: Several smaller locks can increase overlap but make ordering and correctness harder.

More concurrency is useful only when the result remains correct.

Further reading

Semaphores and waiting for conditions

Counting semaphore: Represent a limited number of permits, such as three available buffers.

Condition variable: Wait for a condition on shared state, checking the predicate under the associated lock.

A permit count and ownership of a mutex express different contracts.

Inter-process communication

Shared memory: Processes exchange data through an explicitly shared region; access still needs coordination.

Messages: Queues, pipes or sockets convey data; capacity and receiver behaviour affect progress.

Communication moves the coordination problem; it does not remove it.

Deadlock conditions

Mutual exclusion: At least one resource is held exclusively.

Hold and wait: A worker keeps one resource while requesting another.

No resource pre-emption: An owned resource is not forcibly reclaimed.

Circular wait: A cycle links workers waiting for one another’s resources.

All four are necessary for the classical resource deadlock model.

Further reading

Investigation OS-602

Fault: A owns spool and waits for log. B owns log and waits for spool.

Remedy: Make both acquire spool before log. Observe waiting without circular dependency.

A consistent total order prevents this cycle.

Prevention, detection and recovery

Prevent: Use an acquisition rule that makes a necessary deadlock condition impossible.

Detect and recover: Identify a cycle, then abort or restart selected work with a defined recovery policy.

Recovery must account for incomplete work and shared-state consistency.

Further reading

Efficiency needs a workload

State the workload: How many requests arrive, what each needs, and which resources they share.

State the measure: Completion time, throughput, response latency, utilisation or another relevant result.

A high utilisation figure is not, by itself, evidence of good service.

Further reading

Investigation OS-603

Hold work constant: Run 12 requests with 1 core and 6 ms device service; then try 2 cores.

Target the bottleneck: Restore 1 core and reduce device service to 2 ms. Compare completed work and elapsed time.

Changing one resource at a time makes the evidence interpretable.

Interpreting the comparison

Baseline: 12 / 74 ≈ 0.162 requests/ms. CPU utilisation ≈ 32.4%; device ≈ 97.3%.

Faster device: 12 / 26 ≈ 0.462 requests/ms. CPU and device utilisation ≈ 92.3%.

Two cores leave batch completion at 74 ms in this model.

Evidence and model limitations

Supported conclusion: The trace explains the fault or performance effect under these stated conditions.

Further evidence: Repeat representative workloads; inspect contention, queueing, latency and configuration.

Explain the mechanism, the measured consequence and what remains uncertain.
