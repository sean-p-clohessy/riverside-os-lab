Files, directories and metadata

Contents: A file exposes data through an operating-system interface. Its format is usually interpreted by applications.

Metadata: Ownership, permissions, size and times describe or control the file; directories organise names.

The filename, the metadata and the stored bytes are different concerns.

Path lookup and permissions

Directory search: The process needs permission to traverse the directory components of a path.

Requested operation: Opening for reading also requires the applicable file-access permission.

Directory read and directory search have different meanings in POSIX-style systems.

Investigation OS-701

Restore required access: Let the readers group search the directory and read the file.

Retest the boundary: Confirm the guest still cannot open the report. Inspect where a denied request stops.

A successful read and least privilege are separate checks.

A cache-miss read

Request path: Application → system call → access checks and file-system lookup → driver request.

Completion path: Device completes → OS handles completion → waiting work becomes ready → data returns.

Becoming ready does not mean immediately running.

Drivers, interrupts and DMA

Driver: Translates OS requests into device-specific operations and handles device interactions.

Interrupt / DMA: An interrupt can signal an event; DMA transfers data without CPU copying every byte.

The CPU still configures, coordinates and handles completion.

Further reading

Buffering, caching and spooling

Buffering: Temporarily hold data between producers and consumers with different rates.

Caching: Retain data for likely reuse to avoid repeated expensive work.

Spooling: Queue jobs for a device, such as print jobs awaiting a printer.

These mechanisms can coexist; their purposes differ.

Further reading

Investigation OS-702

Burst versus service: 3 records arrive per tick for 4 ticks. The device persists 1 record per tick.

Compare policies: Increase the buffer or apply backpressure. Then interrupt the power after tick 4.

Record acceptance is not the same event as durable storage.

Queue capacity and backpressure

Larger buffer: Absorbs a finite burst, consuming more memory and potentially retaining more pending work.

Backpressure: Slows admission or holds work upstream; the sender must be able to wait safely.

Neither policy makes this device persist more than 1 record per tick.

Durability and failure

Visible to the application: A request may be accepted into volatile memory before physical persistence.

Survives failure: Durability depends on the storage stack, write policy, flush guarantees and power-loss behaviour.

The lab deliberately separates accepted, persisted, dropped and lost records.

Constrained operating environments

Limited resources: RAM, CPU service, storage, power and communication capacity constrain design.

Timing and failure: A control action may have a deadline; missing it can matter more than average throughput.

A desktop’s preferred trade-off may be unsuitable for a controller.

Further reading

Firmware, RTOS and application

Firmware image: Can package application code, drivers, configuration and an RTOS together.

RTOS responsibilities: Provides facilities such as task scheduling and synchronisation; application code supplies control behaviour.

Firmware and an IoT operating system are not mutually exclusive labels.

Further reading

Deadlines and response time

Control task: Release every 5 ms; needs 1 ms CPU service; deadline 2 ms after release.

Telemetry task: Release every 5 ms; needs 3 ms CPU service; deadline 5 ms after release.

Control finishing at 4 ms misses its first deadline at 2 ms.

Investigation OS-703

Timing experiment: Compare telemetry-first and control-first execution over 20 ms.

Memory experiment: Test queue allocations against 64 KiB RAM. Explain the trade-off before accepting a configuration.

A configuration must both fit and behave correctly under the stated workload.

Priority inversion and shared resources

Unexpected delay: A high-priority task can wait for a lock held by lower-priority work.

Mitigation: Priority inheritance or ceiling protocols can address some blocking patterns; design still needs analysis.

High priority does not remove dependency on lower-priority work.

Resource budgets and safe operation

Budget: Account for stacks, queues, code/data and worst-case demand; retain justified headroom.

Failure behaviour: Define safe outputs, detection, restart behaviour and how state is recovered.

A watchdog can detect loss of progress; it cannot repair a flawed control design.

Evaluating OS services together

General-purpose roles: Balance compatibility, accessibility, administration, isolation and throughput for staff and services.

Controller role: Balance bounded response, memory use, reliability, update strategy and device support.

Judge the whole deployment and its requirements, not a feature count.
